## From Business Problem to a Reliable AI Solution
### من فهم المشكلة إلى تصميم حل أتمتة موثوق

---

## 1. Purpose of This Document | الهدف من الوثيقة

هذه الوثيقة مرجع هندسي يساعدكِ على تحويل مشكلة تجارية حقيقية إلى حل أتمتة مدروس، من خلال فهم العملية الحالية، وتقييم فرصة الأتمتة، واختيار المعمارية المناسبة، وتحديد المتطلبات، وتصميم التعامل مع البيانات والأخطاء، وقياس القيمة التجارية، والاستعداد للتشغيل والتسليم.

لا يُطلب منكِ استخدام كل أداة أو تقنية تعلمتِها في هذا الكورس، ولا تعبئة كل قسم بالتفصيل في كل مشروع. المطلوب هو استخدام الأجزاء المناسبة لطبيعة المشكلة، وحجم الحل، ومستوى المخاطر، ومرحلة التنفيذ.

### Engineering Principles | المبادئ الهندسية

1. **Problem Before Tools:** افهمي المشكلة قبل اختيار الأداة.
2. **Simplify Before Automating:** بسّطي العملية قبل أتمتتها.
3. **Requirements Before Implementation:** حددي ما يجب أن يحققه الحل قبل بنائه.
4. **Right Architecture, Not Maximum Complexity:** اختاري أبسط معمارية تحقق المتطلبات.
5. **AI Where It Adds Value:** استخدمي AI عندما تحتاج المهمة إلى قدرات تفسيرية أو لغوية، وليس لمجرد توفره.
6. **Validate Before Acting:** تحققي من المخرجات قبل استخدامها في إجراءات لاحقة.
7. **Design for Failure:** صممي للحالات الاستثنائية، وليس للسيناريو المثالي فقط.
8. **Measure Real Value:** قيسي النتائج الفعلية بدل الاكتفاء بالانطباعات.
9. **Document Decisions:** وثّقي القرارات والافتراضات والقيود المهمة.
10. **Working Is Not the Same as Production-Ready:** نجاح النموذج الأولي لا يعني أن الحل جاهز للتشغيل الفعلي.

# 2. Your Engineering Roadmap | مسار العمل الهندسي

استخدمي هذا المسار لترتيب تفكيركِ وتطوير فكرتكِ خطوة بخطوة.

| المرحلة | السؤال الأساسي | المخرج المتوقع |
|---|---|---|
| 1. Discover | ما المشكلة الحقيقية؟ | Problem Definition |
| 2. Analyze | كيف تعمل العملية اليوم، وأين توجد فرصة التحسين؟ | AS-IS Process Map |
| 3. Decide | ما النهج التقني الأنسب، ولماذا؟ | Architecture Decision |
| 4. Design | كيف سيعمل الحل، وكيف ستتبادل مكوناته البيانات؟ | TO-BE Process & System Design |
| 5. Specify | ما الذي يجب أن يفعله الحل، وما حدود نطاقه؟ | Requirements & Scope |
| 6. Protect | كيف سنتعامل مع البيانات والمخاطر والأعطال؟ | Security & Reliability Plan |
| 7. Evaluate | كيف سنعرف أن الحل يعمل ويحقق القيمة المطلوبة؟ | Test Plan & Success Metrics |
| 8. Deliver | كيف سنقبل الحل ونسلّمه ونحافظ عليه؟ | Acceptance & Handover Plan |

**مهم:** هذا المسار يساعدكِ على ترتيب العمل، لكنه لا يعني أن كل مشروع يجب أن يمر بجميع التفاصيل وبالعمق نفسه. قد تحتاج بعض المشاريع الصغيرة إلى تصميم مختصر، بينما تحتاج الحلول التي تتعامل مع بيانات حساسة أو إجراءات مؤثرة إلى مراجعة أكثر تفصيلًا.

# 3. How to Use This Canvas | كيف تستخدمين الوثيقة؟

خلال تطوير فكرتكِ، صنّفي المعلومات المهمة باستخدام الحالات التالية:

- **Known:** معلومة مؤكدة ومدعومة بمصدر أو دليل.
- **Assumption:** افتراض نستخدمه مؤقتًا ويحتاج إلى التحقق.
- **Unknown:** معلومة لا نعرفها بعد.
- **Decision:** قرار هندسي اتُّخذ مع توضيح مبرراته.
- **Validation Needed:** نقطة تحتاج إلى اختبار أو تحقق قبل الاعتماد عليها.

لا تكتبي الافتراضات على أنها حقائق، ولا تستبدلي البيانات المفقودة بأرقام غير موثقة.

## Minimum Viable Design | الحد الأدنى للتصميم

عند تطوير فكرة جديدة، ابدئي بهذه المخرجات الأساسية:

- [ ] تعريف المشكلة والمستخدم المستفيد.
- [ ] توثيق العملية الحالية.
- [ ] اختيار النهج التقني وتبرير الاختيار.
- [ ] رسم تدفق البيانات والمسؤوليات الأساسية.
- [ ] تحديد المتطلبات والنطاق.
- [ ] تحديد أهم حالات الفشل والمخاطر.
- [ ] تحديد طريقة الاختبار ومؤشرات النجاح.

بعد ذلك، أضيفي تفاصيل التكلفة، والمراقبة، والاستعادة، والتشغيل، والتسليم وفقًا لحاجة المشروع.

**ما المشكلة الفعلية التي نريد حلها؟**

- ما الذي يبدأ العملية (Trigger)؟

### 5.3 Choosing the Right Approach | اختيار النهج التقني

اختاري النهج بناءً على طبيعة المهمة ومتطلباتها.

| Approach | متى يناسب؟ | مثال |
|---|---|---|
| Workflow Automation | عندما تكون الخطوات والقواعد واضحة ويمكن تحديدها مسبقًا | حفظ طلب وإرسال إشعار |
| AI-Powered Workflow | عندما تحتوي خطوة أو أكثر على بيانات تحتاج إلى تفسير، بينما يظل مسار العملية محددًا | استخراج بيانات العميل من رسالة ثم توجيه الطلب وفق قواعد |
| AI Application | عندما يحتاج المستخدم إلى واجهة للتفاعل مع وظيفة أو خدمة يقدمها النظام | تطبيق لاستقبال الطلبات وعرض النتائج |
| AI Assistant | عندما يحتاج المستخدم إلى واجهة محادثة للإجابة أو المساعدة في مهمة | مساعد يجيب عن أسئلة المستخدمين |
| RAG | عندما تحتاج الإجابات إلى الاستناد إلى معرفة أو مستندات محددة | استرجاع سياسات الشركة للإجابة عن سؤال |
| AI Agent | عندما تتطلب المهمة اختيار الخطوات أو الأدوات التالية بصورة ديناميكية ضمن صلاحيات وضوابط محددة | وكيل يجمع معلومات من أدوات معتمدة وفق حالة الطلب |
| Human-in-the-Loop | عندما يحتاج قرار أو إجراء إلى مراجعة أو موافقة بشرية | اعتماد استثناء مالي |
| Hybrid Solution | عندما تكون هناك حاجة إلى دمج أكثر من نهج | AI لاستخراج البيانات، وقواعد للتحقق، وموظف لمراجعة الاستثناءات |

**ملاحظة معمارية:** هذه الخيارات ليست كلها بدائل متنافسة. فـ **RAG** نمط لاسترجاع المعرفة، و**AI Agent** نمط لتنفيذ المهام واتخاذ قرارات حول الخطوات التالية، و**AI Application** واجهة أو تطبيق. يمكن لنظام واحد أن يجمع بينها.

### 6.4 System Flow & Source of Truth
## تدفق البيانات ومصدر الحقيقة

وضّحي كيف تنتقل البيانات بين المكونات، وأين تُحفظ البيانات المعتمدة.

- **Input Source:** من أين يبدأ الطلب؟
- **Processing Components:** ما المكونات التي تعالج البيانات؟
- **AI Component:** ما المهمة المحددة التي ينفذها AI؟
- **System of Record:** ما النظام المعتمد لحفظ البيانات الأساسية؟
- **Output Destination:** أين تذهب النتيجة؟
- **State Management:** كيف نعرف أن الطلب جديد أو قيد المعالجة أو مكتمل أو فاشل؟
- **Failure Path:** ماذا يحدث إذا فشل أحد المكونات؟

**Architecture Diagram:**

أرفقي رسمًا بسيطًا يوضح المكونات والأسهم التي تمثل تدفق البيانات، مثل:

`User → Application → Backend / Webhook → Workflow / AI → Database → Result`

هذا مثال توضيحي فقط، وليس معمارية إلزامية لكل مشروع.

# 9. Reliability & Exception Design
## الاعتمادية والتعامل مع الحالات الاستثنائية

### 9.1 Failure Analysis | تحليل حالات الفشل

حددي كيف يمكن أن يفشل الحل، وكيف سيكتشف الفشل، وما الاستجابة المناسبة.

| Failure Scenario | Possible Cause | Business Impact | Detection Method | System Response | Human Intervention? |
|---|---|---|---|---|---|
| Missing Input | طلب غير مكتمل | معالجة غير صحيحة | Input Validation | طلب المعلومات الناقصة | |
| Invalid AI Output | استجابة غير متوقعة | إجراء لاحق غير صحيح | Schema Validation | رفض النتيجة أو تحويلها للمراجعة | |
| External API Failure | انقطاع الخدمة أو تجاوز حدود الاستخدام | تأخير المعالجة | Error Status / Timeout | إعادة المحاولة عند ملاءمتها أو تسجيل الفشل | |
| Duplicate Request | إعادة الإرسال أو تكرار Webhook | سجلات أو إجراءات مكررة | Unique Identifier / Idempotency Check | منع التكرار غير المقصود | |
| Database Failure | مشكلة اتصال أو صلاحيات | عدم حفظ البيانات | Database Error | إيقاف الخطوات المعتمدة على الحفظ وتسجيل الفشل | |
| Ambiguous AI Result | معلومات ملتبسة | قرار غير صحيح | Validation / Business Rules | طلب توضيح أو تحويل الحالة للمراجعة | |
| Notification Failure | تعطل خدمة الرسائل | عدم وصول الإشعار | Delivery Error | تسجيل الفشل وإعادة المحاولة أو استخدام مسار بديل | |
| Workflow Failure | فشل عقدة أو إعداد | عملية غير مكتملة | Execution Monitoring | تنبيه المسؤول واتباع إجراء الاستعادة | |

عدّلي الجدول حسب المعمارية الفعلية. ليس مطلوبًا تضمين كل حالة في كل مشروع.

### 9.2 Recovery Policy | سياسة الاستعادة

لكل حالة فشل مهمة، حددي:

- **Retry:** هل إعادة المحاولة مناسبة وآمنة؟
- **Idempotency:** هل يمكن أن يؤدي تكرار التنفيذ إلى إنشاء سجل أو إرسال رسالة أو تنفيذ إجراء أكثر من مرة؟
- **Timeout:** متى نعتبر الاستجابة متأخرة؟
- **Fallback:** ماذا يحدث إذا استمرت الخدمة الأساسية في التعطل؟
- **Human Escalation:** من يستقبل الحالة، وما المعلومات التي يحتاج إليها؟
- **Recovery:** كيف نستكمل الطلب المتعثر دون إفساد البيانات؟
- **Audit Trail:** ما المعلومات الضرورية لفهم المشكلة والتحقيق فيها؟

**Engineering Warning:** لا تعيدي تنفيذ إجراء ذي أثر مهم بشكل أعمى. فقد تنجح العملية في النظام الخارجي، لكن لا تصل الاستجابة إلى النظام الذي بدأها، فتؤدي إعادة التنفيذ إلى تكرار غير مقصود.
